# 第 4 天：分层与异常处理

## 1. 今天的学习目标

今天把自选股分组接口从“能写入数据库”推进到“能查询、能分层、出错时返回安全响应”。

- API 层负责 HTTP 路由、请求校验和响应转换。
- 数据访问层负责 SQLAlchemy 查询和写入。
- 异常处理器负责把未预期异常转换成统一的 HTTP 500 响应。
- 日志保留开发者排查异常所需的堆栈信息，但不把内部细节返回给用户。

## 2. 今天完成的功能

### 查询自选股分组

`GET /api/v1/watchlists` 从 PostgreSQL 查询所有分组，并按 `id` 排序。

接口返回示例：

```json
[
  {"id": 1, "name": "长期观察"}
]
```

没有分组时返回空列表 `[]`。

### 数据访问层

文件：`app/watchlists/repository.py`

- `create_watchlist(session, name)`：创建并提交一个分组。
- `get_watchlists(session)`：查询并返回所有分组。

API 层不再直接编写 `select(Watchlist)` 或 `session.add()`，而是调用数据访问函数。

### 统一异常响应

应用注册了统一的未预期异常处理器：

- HTTP 状态码：`500`。
- 返回内容：`{"detail": "服务器内部错误"}`。
- 日志记录完整异常堆栈。
- 返回内容不包含数据库连接细节或异常文本。

这里使用的是教学阶段的统一兜底处理器。后续会继续增加更具体的业务异常和数据库异常处理，避免所有错误都被归为 500。

## 3. 今天遇到的问题

### 源文件误放到 `__pycache__`

`__pycache__` 是 Python 自动生成字节码缓存的目录，不是源代码目录。源文件必须位于：

```text
app/watchlists/__init__.py
app/watchlists/repository.py
```

### 测试客户端重新抛出异常

`httpx.ASGITransport` 默认会把应用内部异常重新抛给测试。测试异常响应时使用：

```python
raise_app_exceptions=False
```

这样才能验证 FastAPI 异常处理器实际返回的 HTTP 500 响应。

### 导入顺序

Ruff 的 `I001` 规则要求导入按标准库、第三方库、项目内模块分组，并在组之间空行。

## 5. 我对分层的理解

API 层的职责：API 层负责 HTTP 路由、请求校验和响应转换。

数据访问层的职责：数据访问层负责 SQLAlchemy 查询和写入


为什么不能把 SQL 查询都写在路由函数里：这样会让路由函数同时负责 HTTP、业务逻辑和数据库操作，代码难以测试和维护。分层以后，每一部分职责更清楚，也更容易替换和复用。
