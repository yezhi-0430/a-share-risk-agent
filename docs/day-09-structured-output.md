# Day 9：结构化输出

## 数据约定

风险摘要包含五个必填字段：facts（事实）、inferences（推断）、unknowns（未知信息）、risk_level（风险等级）、sources（来源）。除风险等级外，其余字段均为字符串列表。

风险等级允许 low、medium、high、unknown。unknown 是明确表示无法判断的合法值；遗漏字段仍然校验失败。格式校验通过不等于事实真实、推断可靠或来源已经核实。

## 调用流程

1. RiskSummary 用 Pydantic 定义结构，并生成 JSON Schema。
2. generate_risk_summary 将格式要求与 Schema 放入 system 消息，将输入数据放入 user 消息。
3. 通过 Day 8 的统一 chat 接口获取模型回答。
4. parse_risk_summary 解析 JSON 并校验字段，将 ValidationError 转为 RiskSummaryParseError。
5. POST /api/v1/risk-summary 接收 input_text，成功时返回摘要；模型输出解析失败时返回 HTTP 502，detail 为“模型输出格式无效”。路由已注册到主应用。

当前采用提示词约束加本地校验，没有启用供应商的原生 JSON Schema 约束模式。提示词不能保证输出符合要求，所以本地校验必须保留。当前 Pydantic 模型默认忽略额外字段，尚未要求拒绝额外字段。

## 离线验证

tests/unit/test_risk_samples.py 包含 20 条独立样例：

- 3 条正常 JSON：中文、Unicode 转义、多行及外围空白。
- 8 条无效文本：空字符串、纯空白、普通文字、截断 JSON、单引号、尾逗号、Markdown 代码块、说明文字前缀。
- 5 条缺失字段：逐一遗漏五个必填字段。
- 4 条结构错误：facts 为字符串、非法风险等级、sources 为 null、根节点为数组。

正常样例返回 200，异常样例返回 502。每条样例之后，在同一应用上再次发送正常请求，确认仍能成功处理。自动测试使用假模型，不调用真实服务。

本次全套测试结果：102 passed，另有两条既有依赖弃用警告。全项目 Ruff 代码检查通过，Day 9 新增 Python 文件已统一格式。

## 真实调用验证

已通过本地 Settings 和模型工厂直接调用一次真实千问，再由 generate_risk_summary 解析回答。输入为虚构的昨日收盘价 10 元、今日收盘价 9 元，并明确缺少成交量、公司身份、公告和评级规则。

结果：五个字段通过 Pydantic 校验，risk_level 为 unknown，sources 注明用户提供的虚构数据。此次验证覆盖真实客户端与解析链路；HTTP 接口通过离线测试验证，没有额外发起真实 HTTP 接口请求。

用户随后也在项目终端亲自运行了真实调用。输出成功打印，截图中可见 unknowns 列出缺失信息，risk_level 为 unknown，sources 为用户提供的虚构数据。

观察：模型把可计算的价格变化放在 inferences 中。这说明结构校验无法保证内容分类正确。后续应由 Python 计算金融指标，再让模型解释结果。

## 口头复盘提纲

采用口头问答，一次一题；先请用户用自己的话解释，答不清时结合今天的样例说明，再换一个例子确认。预计 15–20 分钟，可按实际理解速度调整。

### 第一组：为什么要结构化

1. 相比一段自由文本，固定五个字段对程序有什么帮助？
2. facts、inferences、unknowns、risk_level、sources 分别记录什么？用今天的虚构价格举例。
3. 没有提供成交量时，应该怎样记录？为什么不能补一个估计值充当事实？

### 第二组：校验能保证什么

4. JSON 语法正确，是否一定能通过 RiskSummary 校验？举一个反例。
5. risk_level 缺失、取值 unknown、取值 safe，分别会怎样？
6. facts 写成字符串而不是字符串列表，会发生什么？
7. 格式正确但来源是编造的，Pydantic 是否一定能发现？

### 第三组：从回答到接口

8. 为什么提示词里已经附上 Schema，拿到回答后仍要校验？
9. 模型返回不完整 JSON 时，错误如何从 ValidationError 变为 RiskSummaryParseError，再变成 HTTP 502？
10. 抛出自定义异常是否就完成了接口错误处理？调用方还要做什么？
11. 为什么临时测试应用能访问接口，而主应用还需要 include_router？

### 第四组：测试和真实调用

12. 20 条样例里，为什么既检查错误响应，也在之后再发一条正常请求？
13. 假模型测试和今天亲自运行的真实千问调用，分别验证了什么？
14. 结合刚才真实输出解释 unknown 和来源字段；能否据此宣称分析内容一定可靠？

## 本次复盘结果（2026-10-07）

- 能直接判断：结构化输出便于程序读取和检查；unknown 是合法风险等级而遗漏字段不合法；假模型测试不能验证真实 API Key；用户数据不能标成交易所官方来源。
- 经举例说明后确认：可由已有记录核对的内容放入 facts；预测和分析属于 inferences，但依据不足时不应凭空给出结论；缺少成交量应在 unknowns 中明确记录。
- 字段类型需要继续巩固：最初将字符串列表误认为字典，随后能识别列表使用 []。综合题中 sources 的字符串与列表区别仍需提示，说明后能判断问题在类型。

- 错误处理流程经说明后确认：try 尝试执行，except 捕获错误；接口将 RiskSummaryParseError 转换为 HTTP 502。坏回答之后再发正常请求，是为了验证后续请求仍能处理。
